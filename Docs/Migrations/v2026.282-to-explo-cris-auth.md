# Migrating from v2026.282 to explo/cris-auth

This guide lists what a repository (or a World) that uses the CK stack must change to move from the
**v2026.282.0** release (`Published/v2026.282.0.json`) to the packages of the **`explo/cris-auth`** branch.

The branch replaces WebFrontAuth (`CK.AspNet.Auth` and the packages built on it) with an authentication made of Cris
commands and an **Authentication Center** (the "AuthCenter") reached over CK-AppIdentity. **An application uses one
stack:** an application that upgrades its CK packages to this version migrates its authentication at the same time.

Each item below has an identifier, a **Detect** step (what to search for: it is meant to be scripted), the **Do** step,
and sometimes a **Check**. Apply them in order: the package changes (M1) bring the compilation errors that the
following items fix.

**The branch targets Angular 22** (the released version targets Angular 20): read **M21 before the first build**. Its
prerequisites (Node, a committed Angular app) must be met before the builder of an Angular application runs on the new
packages, because that run upgrades the application.

## M2. The CK-AppIdentity configuration: "Defaults", no inheritance

The `CK-AppIdentity` configuration no longer inherits a key from an enclosing level. Default values are written in
explicit **`"Defaults"`** sections, which can appear at every level (root, tenant domain, group).

**Detect:** in every `appsettings*.json`, in-memory configuration (`c["..."] = ...`) and `ApplicationIdentityServiceConfiguration.Create`
callback: a key at the root, a tenant domain or a group (a *structural* level) other than its identity and structure
keys.

The structural levels accept only: `FullName`, `DomainName`, `PartyName`, `EnvironmentName`, `Parties`, `Local`,
`Defaults`, and at the root `StoreRootPath`, `TrashBinRetention`, `StrictConfigurationMode`. **Any other key there is a
start-up error** whose message says to move it.

**Also detect a `"Local"` section inside a `"Local"` section** (a former copy): it is not an error, but nothing reads it
(the keys are read at `CK-AppIdentity:Local:<Key>`). Move the keys it holds that are missing from the enclosing
`"Local"` up one level, and remove it.

**Do:** for each such key:
- if it configures the application (the local party) itself, move it into the level's **`"Local"`** section;
- if it was meant as a default for the parties below (the remotes), move it into a **`"Defaults"`** section at that
  level;
- if it was both, write it in both.

```jsonc
// Before (the root key was inherited by the remotes)
"CK-AppIdentity": {
  "FullName": "Acme/$Server",
  "AllowFeatures": "SomeFeature",
  "ListeningAddress": [ "tcp:127.0.0.1:37300" ],
  "Parties": [ ... ]
}
// After
"CK-AppIdentity": {
  "FullName": "Acme/$Server",
  "Local": { "AllowFeatures": "SomeFeature" },
  "Defaults": { "ListeningAddress": [ "tcp:127.0.0.1:37300" ] },
  "Parties": [ ... ]
}
```

- `AllowFeatures` / `DisallowFeatures` stay a delta: the `"Defaults"` from the farthest to the nearest, then the
  party's own keys. The same for `Assemblies` / `DefaultAssembly`.
- A remote party's entry has no `"Local"` nor `"Defaults"`; a `"Defaults"` holds no identity or structure key.
- `"RootStorePath"` was a misspelling that was silently ignored: the key is **`StoreRootPath`**.

**Check:** the application starts without a configuration error, and a party that should allow a feature does (a
remote that relied on an inherited `AllowFeatures` now needs it in a `"Defaults"` or in its own entry).

## M3. The application host: WebFrontAuth becomes the AuthCenter

**Detect:** `AddWebFrontAuth(`, `WebFrontAuthOptions`, `new AuthenticationBuilder(`, `UseAuthentication()` used for
WebFrontAuth, `UseMiddleware<CrisMiddleware>()`, the `/.webfront` routes in clients.

**Choose the shape:**
- **One application** (the most common deployment: the front application directly on its backend party): the
  application **is its own AuthCenter**: `CK.AppIdentity.AuthCenter.Local` + `CK.Cris.AspNet.Authentication`.
- **Several applications:** one AuthCenter application (`.Local`, the database, the login providers) and fronts
  (`CK.AppIdentity.AuthCenter.Remote` + `CK.Cris.AspNet.Authentication`) connected to it by CK-AppIdentity. The
  reference is the CK-Sample-AspNetAuth repository (its `Auth3`, `Front` and `Admin` hosts: a party is named after
  what it is, not after the feature it implements; `Sample/Auth3/$Auth3` is the domain controller of the `Sample/Auth3`
  domain, the party named after its domain, and it is also the AuthCenter).

**Do (one application):**

1. The packages (in the application's "App" project): `CK.AppIdentity.AuthCenter.Local`,
   `CK.Cris.AspNet.Authentication`, and per login scheme its Angular package (`CK.Ng.Cris.AspNet.Authentication.Basic`...,
   see M7) or, without an Angular front, its `CK.Cris.Authentication.<Scheme>` package. The database providers stay (`CK.DB.User.UserPassword` for Basic: it holds the login
   provider of the scheme).
2. The host: remove `AddWebFrontAuth`, the `AuthenticationBuilder`, `UseAuthentication` for WebFrontAuth,
   `UseMiddleware<CrisMiddleware>()` and the host's `AddDataProtection()` (see below). The host is a party with the
   "HttpEndpoint" feature (M15, M18, M29): the package contributes the Cris authentication and Cris to its endpoint
   (`EnableCrisAuthentication`, which enables Cris): the host writes nothing for them.

   `CK.AppIdentity.KeyManagement` registers the DataProtection, keyed on the identity's full name rather than the content
   root path: remove the host's `AddDataProtection()`. **This is a one-time break:** what was protected under the former
   discriminator can't be read anymore. That includes the identity keys (delete the party's folder in the identity store:
   the key is recreated, and the remotes that pinned it must pin it again) and the authentication cookies (the users log in
   again).
3. The configuration (`appsettings.json`): the local party allows the feature; its settings are its `"AuthCenter"`
   section.
   ```jsonc
   "CK-AppIdentity": {
     "FullName": "MyApp/$Server",
     "Local": {
       "AllowFeatures": "AuthCenter",
       "AuthCenter": {
         "SessionLifetime": "1.00:00:00",
         "CriticalLifetimes": { "Basic": "00:05:00" }
       }
     },
     "Parties": []
   }
   ```
   There is no `"AuthCenter": true` designation (it is an error): allowing the feature is the opt-in. The AuthCenter
   is an asymmetric feature: its name is `"AuthCenter"` in the `"Local"` of a party and `"AuthCenterRemote"` on a
   remote, and the `"Local"` gives the role.
   - **With several applications, the AuthCenter** allows `"AuthCenter"` in its `"Local"` and `"AuthCenterRemote"`
     on its fronts (the remotes that use it).
   - **A front** doesn't allow `"AuthCenter"` in its `"Local"`, and allows `"AuthCenterRemote"` on the one remote
     that is its AuthCenter.
   - **A wrong name fails the start:** a `"Local"` that allows only `"AuthCenterRemote"`, or a remote that allows only
     `"AuthCenter"`.
   - **The AuthCenter must announce it:** a front checks that the remote it uses announces being the AuthCenter. An
     AuthCenter that forgets `"AuthCenter"` in its `"Local"` is an error when it connects.

**`CK.AspNet` is no longer brought by the authentication:** a host that used `UseCKMonitoring()`, `CKBuild( map )` or
`GetBuilderMonitor()` on a `WebApplicationBuilder` fails to compile: it becomes a party (M15, M18, M29).

**The WebFrontAuth options:**

| WebFrontAuthOptions | AuthCenter (`Local:AuthCenter`) |
|---|---|
| `ExpireTimeSpan`, `SlidingExpirationTime` | `SessionLifetime` (default 1 day; the session slides on each refresh) |
| `SchemesCriticalTimeSpan` | `CriticalLifetimes:<scheme>` (and `CriticalLifetime` for the other schemes) |
| (none) | `TokenLifetime` (default 10 minutes), `RefreshGraceWindow` (default 1 minute, at most 5) |

**The Critical level differs:** WebFrontAuth gave no Critical level unless `SchemesCriticalTimeSpan` said so; the
AuthCenter gives **5 minutes** of Critical level after a Basic or passkey login by default (`CriticalLifetime`).
`00:00:00` for a scheme means "never Critical". Password changes, passkey registration, impersonation and
administration require the Critical level.

**The HTTP routes:**
- `/.webfront/*` is gone. The session commands (login, refresh, logout, impersonation...) are Cris commands posted to
  **`/.cris/auth`**; the other commands go to `/.cris`.
- A bearer token is accepted **only with its session's binding cookie** (path `/.cris`): a stolen token alone is
  anonymous. The refresh secret is a cookie of path `/.cris/auth`.
- `/.cris` and `/.cris/auth` accept only a **same-origin** JSON `POST` (a cross-site `Origin` or `Sec-Fetch-Site` is
  refused with 403, another media type with 415). A front served from another origin must be served through the
  application (a proxy), not called with CORS.
- The authentication applies to the Cris commands only: there is no HTTP interceptor adding the token to other
  requests (controllers, files).

**`CK.DB.GuestActor`:** `GuestActorDirectLoginAllower` (a WebFrontAuth direct login of the guests) is removed; the
package keeps its data model. There is no guest login scheme in the new stack yet.

**Check:** a Basic login on `/.cris/auth` returns a `SessionResult` with a token; a Normal command sent with the token
(and the cookies) is accepted; after the logout, the same command is refused.

## M4. The C# authentication API

**Detect:** `IAuthenticationInfo`, `IUserInfo`, `StdAuthenticationTypeSystem`, `IAuthenticationTypeSystem`,
`AuthenticationInfoTokenService`, `IWebFrontAuth*`, `.User.UserId`, `.ActualUser`, `.UnsafeUser`, `IAuthenticationResult`,
`ILogoutCommand`, `IRefreshAuthenticationCommand`, `IPocoAuthenticationInfo`, `IPocoUserInfo`,
`CrisWebFrontAuthCommandHandler`, `using CK.AspNet.Auth`.

**Do:**

| Old (CK.Auth.Abstractions, CK.Cris.Auth, CK.IO.Auth.Basic) | New |
|---|---|
| `IAuthenticationInfo` (an ambient service) | `AuthenticationInfo` (sealed class, ambient service, namespace `CK.Core`, package `CK.AuthenticationInfo`) |
| `info.User`, `info.ActualUser` | `info.Actor`, `info.ActualActor` (the anonymous below the Normal level) |
| `info.UnsafeUser`, `info.UnsafeActualUser` | `info.UnsafeActor`, `info.UnsafeActualActor` |
| `user.UserId`, `user.UserName` | `actor.ActorId`, `actor.ActorName` |
| `info.Level`, `info.DeviceId` | `info.UnsafeActor.Level` (each actor has its level), `info.DeviceId` |
| `StdAuthenticationTypeSystem` ... `.Create( userInfo, expires )` | `AuthenticationInfo.Create( new ActorInfo( id, name, level ), expires, criticalExpires, deviceId, utcNow )` |
| The users read by WebFrontAuth | `IActorInfoProvider` (implemented by `CK.DB.Auth`) |
| `IBasicLoginCommand` (CK.IO.Auth.Basic) | `CK.IO.Authentication.Basic.IBasicLoginCommand` (result: `ISessionResult`) |
| `ILogoutCommand`, `IRefreshAuthenticationCommand` | `ILogoutSessionCommand`, `IRefreshSessionCommand` (CK.IO.Authentication) |
| `IAuthenticationResult` (`Info`, `Token`, `Success`) | `ISessionResult` (`Info`, `Token`, `Success`, `RememberMe`) |
| `CrisAuthenticationService` (CK.Cris.Auth) | `CrisAuthenticationService` (CK.Cris.Authentication, namespace `CK.Auth`): same validation of the parts |

- The validation messages of the parts keep their text ("Invalid authentication level: ...", "Invalid actor identifier:
  ...", "Invalid device identifier: ...") and get resource names (`Authentication.ActorMismatch`,
  `Authentication.NormalLevelRequired`, `Authentication.CriticalLevelRequired`).
- A command or event executed later (a delayed or background command) restores its `AuthenticationInfo` from its
  parts: the actors are read by the `IActorInfoProvider`, and the restoration fails if an actor is not found.
- A login provider of a scheme is an `ILoginProvider` (in the AuthCenter); a login is never handled in a database
  package: the scheme packages (`CK.Cris.Authentication.Basic`...) hold the session command handlers.
- Remove `using CK.Auth;` from a file that used only the old abstractions: without `CK.IO.Auth` in its references the
  namespace no longer exists (CS0234).

**Check:** the solution compiles without any reference to the old types.

## M5. The routed events are renamed local events

**Detect:** `[RoutedEvent]`, `[RoutedEventHandler]`, `RoutedEventAttribute`, `RoutedEventHandlerAttribute`,
`CrisPocoKind.RoutedEvent`, `CrisPocoKind.RoutedImmediateEvent`.

**Do:** `[RoutedEvent]` → `[LocalEvent]`, `[RoutedEventHandler]` → `[LocalEventHandler]`, `CrisPocoKind.RoutedEvent` →
`CrisPocoKind.LocalEvent`, `CrisPocoKind.RoutedImmediateEvent` → `CrisPocoKind.LocalImmediateEvent`. Same semantics:
these events are local notifications, raised where the command executes.

## M6. CK.Configuration: the lookup API is obsolete

The lookup methods that walk up the parent sections are `[Obsolete]` (they keep their semantics); a new API resolves a
key as "its own value, otherwise the nearest `"Defaults"` section above it".

**Detect:** the obsolete warnings (CS0618) on `TryLookupSection`, `TryLookupValue`, `LookupAllSection`,
`LookupAllSectionWithDistance`, the typed `TryLookupXxxValue` / `LookupXxxValue`, `AssemblyConfiguration.Create`.

**Do:** use `TryResolveSection`, `TryResolveValue`, `ResolveAllSection(WithDistance)`, `TryResolveXxxValue`,
`ResolveXxxValue`, `AssemblyConfiguration.Resolve`, and move the configuration values that relied on the parent lookup
into `"Defaults"` sections (`ConfigurationSectionExtension.DefaultsKey`). A configuration that is not a CK-AppIdentity
one can keep the obsolete API for now.

## M7. The TypeScript and Angular front

**Detect:** in the C# of the packages: `AspNetAuthPackage`, `AspNetAuthBasicPackage`, `CrisAspNetAuthPackage`,
`using CK.Ng.AspNet.Auth`, `using CK.Ng.Cris.AspNet.Auth`; in the TypeScript and the transformers (`*.t`):
`authenticationInfo().user`, `authenticationInfo().level`, `authenticationInfo().actualUser`,
`authenticationInfo.user`, `authenticationInfo.level`, `authService.basicLogin(`, `unsafeDirectLogin(`,
`availableSchemes`, `CK/Ng/AspNet/Auth/`.
- `authenticationInfo().unsafeActor` is the new API.
- A `basicLogin(` function that returns a `BasicLoginCommand` is the helper that M8 recommends.

Neither is a leftover.

**Do, the packages:**

| Old | New |
|---|---|
| `CK.Ng.AspNet.Auth.AspNetAuthPackage` | `CK.Ng.Cris.AspNet.Authentication.NgCrisAuthenticationPackage` |
| `CK.Ng.AspNet.Auth.Basic.AspNetAuthBasicPackage` | `CK.Ng.Cris.AspNet.Authentication.Basic.NgCrisAuthenticationBasicPackage` |

## M11. Poco `Clone()` and `Create<T>()`

Every Poco is now a factory of any other Poco (CK.StObj.Model, `PocoExtension`), with generated code (no reflection,
no serialization):

```csharp
T Clone<T>( this T poco ) where T : class, IPoco;                         // A deep copy.
T Create<T>( this IPoco source ) where T : class, IPoco;                  // A new T from what the source shares with it.
T Create<T>( this IPoco source, Action<T> configure ) where T : class, IPoco;
```

**`Create<T>` copies the shared parts only:** a property is copied when it is declared by an abstract Poco (a part,
`[CKTypeDefiner]`, like `ICommandCurrentCulture`, `ICommandAuthNormal`, `ICommandTargetParty`...) that both types
implement. Two properties that only have the same name are **not** copied. The copy is deep (nested Pocos and
collections are copied, immutable values are shared). Same type: a clone; nothing shared: a new default `T`.

**Detect (1), a result or a command built by copying from the command:** a command handler that takes a
`PocoDirectory` (or uses `cmd.CreateResult(...)`) and assigns properties of the command to the new Poco
(`r.X = cmd.X;`, `c.CurrentCultureName = cmd.CurrentCultureName;`, `c.ActorId = cmd.ActorId;`...).

**Do:** create the new Poco from the command: `cmd.Create<TResult>( r => ... )` (or `cmd.Create<INextCommand>( ... )`).
The `PocoDirectory` dependency of the handler often disappears, and so do the copies of the properties of the shared
parts. The properties that are not in a shared part are set explicitly: never create a part only to share them (a part
carries a semantics, like `ICommandCurrentCulture`; properties that merely have the same name are not one).

```csharp
// Before
[CommandHandler]
public async Task<IExecutionIdentity> HandleAsync( IAskLaterQCommand command, AuthenticationInfo info, PocoDirectory pocos, ... )
{
    var whoAmI = pocos.Create<IWhoAmIQCommand>( c =>
    {
        c.TargetPartyFullName = command.TargetPartyFullName;
        c.ActorId = info.Actor.ActorId;
    } );
    ...
// After: the ICommandAuthNormal part (the validated ActorId) is shared; TargetPartyFullName is not in a shared part.
[CommandHandler]
public async Task<IExecutionIdentity> HandleAsync( IAskLaterQCommand command, ... )
{
    var whoAmI = command.Create<IWhoAmIQCommand>( c => c.TargetPartyFullName = command.TargetPartyFullName );
    ...
```

`cmd.CreateResult(...)` (CK.Cris) is unchanged: it creates an empty result. Use it when the result shares nothing with
the command.

**Detect (2), a clone by serialization:** a Poco written to JSON and read back to copy it (`WriteJson` then `ReadJson`
of the same Poco, often in a helper named `Clone` or `DeepClone`).

**Do:** `poco.Clone()`. The semantics are the ones of the round-trip it replaces: a tree (a shared reference is copied
twice, a cycle is not supported).

## M14. The TypeScript configurations: package selection and client applications

A `<TypeScript>` configuration selects its packages, and it can be a **client application** that its host serves.

**The package selection (behavior):** the packages listed in the `<Types>` of a configuration are the roots of its
selection (when none is listed: all the non optional packages); the configuration gets their closure (computed from the
types: requirements, children, mappings), and its `<ExcludedTypes>` are never selected. Only the selected packages are
handled: their resources, their transformers, their `[RegisterTypeScriptType]` (the type set of the configuration) and
their npm libraries (`[TypeScriptImportLibrary]`). A type name of the `<Types>` or `<ExcludedTypes>` can be a pattern
(`"Acme.Front.*, Acme.Front"`, `"*, Acme.Commands"`): see the README of CK.TypeScript.

**The `/.cris` type set (behavior):** a request to `/.cris` is read with the type set of its `TypeFilterName` query
parameter ("TypeScript" when absent); an unknown `TypeFilterName` is a 400 Bad Request. The generated `HttpCrisEndpoint`
sends the one of its configuration; a raw request (a test, a `fetch`) to a named configuration passes it
(`/.cris?TypeFilterName=TypeScriptApp`).

**Detect:** in the builders and the `CKSetup.xml`: `TargetProjectPath`, `TypeFilterName`, `<Types>` that list packages,
`EnsureDefaultTypeScriptAspectConfiguration`; in the hosts: the serving of an Angular `dist` (`PhysicalFileProvider`,
`UseStaticFiles`, `MapFallbackToFile`), `MapForwarder` / `AddHttpForwarder` / `Yarp.ReverseProxy` to a dev server,
`UseSpa` / `UseProxyToSpaDevelopmentServer` and the `Microsoft.AspNetCore.SpaServices.Extensions` reference;
requests to `/.cris` outside the generated client.

**Do (recommended), the configuration:** name the configuration and give it its kind and its dev server port:

```xml
<TypeScript>
  <Multiple>
    <TypeScript Name="App" Kind="DefaultApp" DevServerPort="4200" />
    <TypeScript Name="MiniApp" Kind="App" DevServerPort="4201">
      <Types>...</Types>
    </TypeScript>
  </Multiple>
</TypeScript>
```

or, in a builder:

```csharp
var ts = builder.EnsureDefaultTypeScriptAspectConfiguration();
ts.Name = "App";
ts.Kind = ClientKind.DefaultApp;
ts.DevServerPort = 4300;
```

The other properties derive from the name: remove them (`TargetProjectPath`, `TypeFilterName`); keep the others
(`IntegrationMode`, the cultures, the `<Types>`...). A configuration that is a single `<TypeScript>` element (no
`<Multiple>`) takes the same three attributes.

**The name and the kind:** a host with one client application gives it `Kind="DefaultApp"` (served at `/`). Its name:
- its Angular project is already in `{ProjectPath}/Clients/{Folder}` (an explicit `TargetProjectPath` to it): the name
  is `{Folder}`, nothing moves;
- otherwise (a `{ApplicationName}.Web` folder...): the name is `App`, and the project moves to `Clients/App` (below).

**The package selection of a `<Types>` that lists no package** (only commands, Pocos...): these types are registered,
but they are not roots: all the non optional packages are selected.

**`EnsureDefaultTypeScriptAspectConfiguration()` (behavior):** it no longer sets the `TargetProjectPath` to
`{HostFolder}/{ApplicationName}.Web`: the engine derives it, `{ProjectPath}/Clients/{Name}` for a named configuration and
`{ProjectPath}/Client` for an unnamed one (the `ProjectPath` of a CKomposableAppBuilder's BinPath is the host folder). A
builder that calls it without a `Name` nor a `TargetProjectPath` and keeps its Angular project in the `{ApplicationName}.Web`
folder names the configuration (and moves the project to `Clients/{Name}`) or sets the `TargetProjectPath`.

| Property | Derived value |
|---|---|
| `TargetProjectPath` | `{ProjectPath}/Clients/{Name}` |
| `TypeFilterName` | `TypeScript{Name}`: an unnamed configuration keeps "TypeScript", so the requests of a renamed one change (see above) |
| Request path | `/` for the `DefaultApp` (at most one per BinPath), `/{kebab-name}` for an `App` (`MiniApp` → `/mini-app/`) |

The Angular engine writes the request path (`baseHref`) and the `DevServerPort` (`serve.options.port`) in the
`angular.json`. The host serves `dist/{folder}/browser` (the folder of the project: `App` for `Clients/App`): when an
existing Angular project moves to `Clients/{Name}`, rename its project in the `angular.json` to the folder name (and its
`buildTarget`s) and remove its `outputPath`. Renaming the `name` of its `package.json` is optional (the serving doesn't
use it): the build runs `yarn install` when the `yarn.lock` has no entry for the workspace of this name (otherwise the
dev server would fail with "Package for ...@workspace:. not found in the project"); commit the updated `yarn.lock`.
The `DevServerPort` is required for a client application and unique in its BinPath; the ports must also differ between
the hosts that run together.

**Moving the project** (`git mv` keeps its history) adds a folder level: fix the relative paths that leave the

   - **Remove** `AddCrisAuthentication`, `UseCrisAuthentication`, `UseCris` and `MapClients`.
   - **The packages do it instead:** their real objects contribute `EnableCrisAuthentication`, `EnableCris` and
     `EnableClients` (`WebApplicationContributions`, CK.AspNet), and the feature applies them to every endpoint.
   - **An application adds its own configuration to an endpoint** with `builder.AddHttpEndpoint( "Main", web => ... )`,
     in one gesture on the `WebApplicationBuilder` (`web.AppendApplicationBuilder( app => ... )` for a middleware).
3. **The configuration:** the endpoints are configured with the party, not by the ASP.NET defaults.
   ```jsonc
   "CK-AppIdentity": {
     "FullName": "MyApp/$Front",
     "Local": {
       "AllowFeatures": "HttpEndpoint",
       "HttpEndpoint": { "Main": { "Urls": "http://localhost:5300" } }
     },
     ...
   }
   ```
   Each child of `Local:HttpEndpoint` is an endpoint, with `Urls` (separated by `;`) or a `Kestrel` section (Kestrel's
   own schema). Remove the root `"Urls"` / `"Kestrel"`.
   The root `Logging` and `AllowedHosts` stay: the web applications of the endpoints read the host's configuration and
   use its logging. The public URL of the party is the endpoint's (M20): an application setting that named the dev
   server's URL goes.
4. **The launch profile:** a Generic Host reads `DOTNET_ENVIRONMENT`, not `ASPNETCORE_ENVIRONMENT`. Remove the
   `applicationUrl` (it sets `ASPNETCORE_URLS`); a `launchUrl` is then absolute:
   ```json
   "Host": {
     "commandName": "Project",
     "launchBrowser": true,
     "launchUrl": "http://localhost:5300",
     "environmentVariables": { "DOTNET_ENVIRONMENT": "Development" }
   }
   ```
5. **The tests:** the host is an `IHost` (`StopAsync` then `Dispose`). A test address is set with
   `CK-AppIdentity:Local:HttpEndpoint:Main:Urls`; a port 0 is resolved, and `HttpEndpointFeatureDriver.Endpoints`
   gives the actual address.

**Behavior:**
- **In Development, the ASP.NET defaults are an error:** the root `urls`, `http_ports` and `https_ports` keys and
  `Kestrel` section, and the `ASPNETCORE_URLS`, `ASPNETCORE_HTTP_PORTS` and `ASPNETCORE_HTTPS_PORTS` environment
  variables. Otherwise they are a warning, and they are ignored.
- **The web applications start once the party is initialized** (all its features set up) and stop before it: no
  request reaches a party that is not whole. A web application that stops by itself stops the host.
- **Only the root party has endpoints,** and every endpoint gets every contribution of the BinPath. A tenant domain
  that allows the feature is an error.
- **The web applications get the host's services:** the singletons are the host's (one instance); the
  container-configured services (`CrisAspNetService`...) are created per web application.

**Check:** the host starts and serves `/.cris` and its client applications (in Development, through their dev
servers). A raw request to `/.cris` passes the `TypeFilterName` of a named configuration (`/.cris?TypeFilterName=TypeScriptApp`):
without it, it is a 400 "Invalid TypeFilterName 'TypeScript'" (M14). CK-Sample-AspNetAuth (the Front and the Admin) is
migrated this way.

`CK.AppIdentity.HttpEndpoint` is in the version line of CK-AspNet (with CK.AspNet, CK.AppHost,
CK.AspNet.WebSocketChannel), not in the one of the other CK.AppIdentity packages.

## M16. The `#Dev` folder of a development solution

The development data of a solution is in a `#Dev` folder at the root of its git working folder (each worktree has its
own). It is automatic: nothing to commit, nothing to configure (CK.AppIdentity.Hosting).
- **The build of each party creates it** (a party: a host that references CK.AppHost (M18), or a project whose
  `<CKAppIdentityParty>` is `true`; nothing else is a party): its `.gitignore` is `*` (git ignores its
  content), the manifest of the party (`#Dev/Parties`), and the launcher `#Dev/Start.ps1`.
  `<CKAppIdentityDevFolder>false</CKAppIdentityDevFolder>` opts a project out.
- **A host in Development uses `#Dev/Store`** when it doesn't configure its `StoreRootPath`: its identity keys, its
  pinned remotes, its running status. Before, it used the store of the user's profile (shared by every checkout).
  In Development, the environment of the party is `#Dev` (its full name is `{DomainName}/${PartyName}/#Dev`), and its
  running status is `#Dev/Store/#Dev/{DomainName}/${PartyName}/DevRunningStatus.json`: `Ready` (started, its outgoing
  remotes connected), `Http` (the endpoints and their URLs), `Clients` (each client application, its `Serving` and its
  `Error`, the failure of its dev server). It is how a host is checked by hand.
- **`#Dev/Start.ps1`** builds the parties, starts them in Development, waits until they are ready (their outgoing
  remotes connected, their HTTP endpoints started, their client applications served), prints their URLs and opens the
  browser; Enter stops them (`-SkipBuild`, `-NoBrowser`, `-Timeout`). It replaces the hand-written launch scripts.

To migrate:
1. Remove a committed `#Dev/.gitignore` (the build writes its own) and a `StoreRootPath` that points to the `#Dev/Store`
   of the solution (like `"../../#Dev/Store"`): the hosts in Development use it anyway. Moving the existing identity
   keys is not required (the parties pin each other again, `AutoTrustKey`).
2. Replace a hand-written launch script of the solution by `#Dev/Start.ps1`.
3. The tests that set `ApplicationIdentityServiceConfiguration.DefaultStoreRootPath` keep their own store (setting it
   disables the dev store); a test of the running status uses the `Create` overload with an explicit `devStoreRootPath`.

**Check:** after a build, `#Dev/Start.ps1` starts the parties and `git status` shows nothing of `#Dev`.
CK-Sample-AspNetAuth is migrated this way.

## M18. One host bootstrap for every party: CK.AppHost

Every host (the "XXX.Host" of an App/Builder/Host solution) starts the same way, so its bootstrap is a package:
**CK.AppHost** (CK-AspNet). The host project is a `.csproj` with its references, a one-line `Program.cs` and its
`appsettings.json`. What a party does is in its packages, its App project and its configuration, never in host code.

**Prerequisite:** the host is a party with the "HttpEndpoint" feature, without pipeline code (M15), and it serves its
client applications with CK.TS.AspNet.Clients (M14). A `WebApplication` host (`WebApplication.CreateBuilder`,
`UseSpa`, `UseStaticFiles`, `UseCors`, `AddControllers`...) does M14 and M15 first.

**Detect:**
- a host `Program.cs` (or a `XXXHost.cs` called by it) that calls `Host.CreateApplicationBuilder` or
  `WebApplication.Create*Builder`, `StObjContextRoot.Load`, `AddStObjMap`, `CKBuild`;
- in the host `.csproj`: an `IncludeGeneratedCode` target, `Compile/Content/None Remove="Clients/**"`,
  `Microsoft.Extensions.Hosting.WindowsServices`, `<CKAppIdentityParty>`;
- in the host code: `AddWindowsService` / `UseWindowsService` / `WindowsServiceHelpers`, `UseSystemd`,
  `GlobalizationFileHelper.SetLocaleTranslationFiles`, data seeding before the run, a `ConnectionString` set from the
  configuration, `AddWebSocketChannel` / `UseWebSocketChannel`, `AddCors` / `UseCors`, `AddControllers`.

**Do:**

1. **The host project:**
   ```xml
   <Project Sdk="Microsoft.NET.Sdk.Web">
     <PropertyGroup>
       <TargetFramework>net10.0</TargetFramework>
       <IsPackable>false</IsPackable>
     </PropertyGroup>
     <ItemGroup>
       <PackageReference Include="CK.AppHost" Version="..." />
       <ProjectReference Include="..\XXX.App\XXX.App.csproj" />
       <ProjectReference Include="..\XXX.Builder\XXX.Builder.csproj" ReferenceOutputAssembly="false" Private="false" />
     </ItemGroup>
   </Project>
   ```
   - `Microsoft.NET.Sdk` with `<OutputType>Exe</OutputType>` works too (a host without ASP.NET Core in its App).
   - **Remove** the `IncludeGeneratedCode` target, the `Clients/**` removals, the `Microsoft.Extensions.Hosting.WindowsServices`
     reference and a `<CKAppIdentityParty>`: the package does it (its `build` files, below). The package references
     that only served the removed host code go too (`Microsoft.AspNetCore.SpaServices.Extensions`,
     `Swashbuckle.AspNetCore`, `Microsoft.AspNetCore.OpenApi`, a `CK.AspNet` or `CK.AppIdentity.Hosting` referenced for
     `CKBuild` or `AddApplicationIdentityServiceConfiguration`: the App project and CK.AppHost bring what is needed).
     Remove also `RunWorkingDirectory` (the package sets it to the project folder: the content root), an `OutputType`
     in a `Microsoft.NET.Sdk.Web` project, the copy of `appsettings.json` (`None Remove` / `Content Include`: the Web
     SDK does it), the `TypeScriptCompileBlocked` / `TypeScriptCompileOnSaveEnabled` properties (the `Clients` folder is
     not part of the project), and `Nullable` / `ImplicitUsings` (no code is left).
   - **The App project** loses the references it had only for the host code: `CK.AspNet` (for `CKBuild`),
     `CK.Monitoring.Hosting` (for `UseCKMonitoring`). It references `CK.AppIdentity.HttpEndpoint` (M15) and
     `CK.TS.AspNet.Clients` (M14).
   - **Building the host runs its builder** (through this reference): `dotnet build` of the host is the whole build.
   - **The reference to the builder is required** (the build fails without it): it orders the builds, and the builder
     writes the generated code in the host's `$StObjGen` folder after its own build. The builder of "XXX.Host" is
     "XXX.Builder"; a host whose project name doesn't end with `.Host` names its builder with
     `<CKAppHostBuilder>ProjectNameOfTheBuilder</CKAppHostBuilder>`.
   - The package's `build` files apply to the host project only (not to a test project that references it): the host
     must be an executable; the generated code (`$StObjGen/**/*.cs`) is compiled; the `Clients` folder is not part of
     the project; the host is a party of the `#Dev` folder (M16: they set `CKAppIdentityParty` to `true`).
2. **`Program.cs`** is one line:
   ```csharp
   await CK.Core.CKomposableAppHost.RunAsync( args );
   ```
   `CKomposableAppHost.Build( args, configure?, contentRoot?, assembly? )` is the whole bootstrap: the content root
   (the current directory, or the folder of the executable for a Windows service), the optional `configure` callback
   on the `HostApplicationBuilder`, `AddWindowsService()` and `AddSystemd()` (they do nothing when the process doesn't
   run as a service), `UseCKMonitoring()`, `AddApplicationIdentityServiceConfiguration()`, the scoped `IActivityMonitor`
   and its `ParallelLogger`, the generated code of the entry assembly (`StObjContextRoot.Load`, `AddStObjMap`), and
   `CKBuild()`. `RunAsync` builds and runs it.
3. **What the host code did, and where it goes:**

   | Host code | Where it goes |
   |---|---|
   | The bootstrap above, the Windows service (`AddWindowsService`, the content root of a service) | CK.AppHost: remove it. |
   | `GlobalizationFileHelper.SetLocaleTranslationFiles( monitor, "{ContentRoot}/locales" )` | The translations of a package: `Res/locales/default.jsonc`, `Res/locales/fr.jsonc`... (one file per culture, flat keys) beside a class of the App project marked `[LocalePackage]` (CK.Globalization.StObj) that implements `IResourceGroup` (or `IResourcePackage`); the engine merges them at build time. Remove the host's `locales` folder: a folder whose content is not real application text (`{}`, `{"Test":"Test"}`, in any layout: `fr.json`, `fr/fr.json`) is just removed. |
   | Data seeding before the run (demo users...) | A real object of the App project with a private `OnHostStartAsync` (below). |
   | `SqlDefaultDatabase.ConnectionString` set from the configuration (`ConnectionStrings:...`) | The connection string is the builder's (`<DefaultDatabaseConnectionString>` of its `CKSetup.xml`). An override that nothing sets (no such key in the `appsettings*.json`, the launch profiles, the scripts) is dead code: remove it. There is no run-time override mechanism: a host that really needs one is a case to raise. |
   | `AddWebSocketChannel()` / `UseWebSocketChannel()` | Nothing: the `WebSocketChannelManager` (CK.AspNet.WebSocketChannel) contributes `EnableWebSocketChannel()` to every endpoint (path `/ws`), provided CK.AspNet.WebSocketChannel is referenced by the App (directly or through a package such as CK.Ng.AspNet.WebSocketChannel). This is the generic channel: it stays (M13 removes the actor channel only). |
   | `AddCrisAuthentication`, `UseCrisAuthentication`, `UseCris`, `MapClients`, `UseRouting`, `UseAuthorization`, `UseStaticFiles`, `UseSpa`, `UseProxyToSpaDevelopmentServer` | Nothing (M14, M15): the packages contribute them; the client applications are served by CK.TS.AspNet.Clients on the origin of the host. |
   | `AddCors` / `UseCors` that allowed the dev server of the Angular application | Nothing: the client application is served on the origin of the host (its dev server is reached through the host). |
   | `UseForwardedHeaders()` without `ForwardedHeadersOptions` (its `ForwardedHeaders` is `None`: it does nothing) | Remove it. |
   | `AddHttpClient()` | Remove it, unless the App's own code uses `IHttpClientFactory` (no package of the stack does). |
   | `AddControllers`, Swagger (`AddSwaggerGen`, `UseSwagger`) | Remove them when there are no controllers. |
   | Other services and middlewares of the application (a configured `UseForwardedHeaders`...) | A real object of the App project that contributes them to the endpoints, or registers the services in its `ConfigureServices` (below). |

   **A real object that runs at the start of the host** (a class of the App project; the method is private, its
   parameters are any singleton or scoped services, resolved in a temporary scope; `OnHostStopAsync` exists too):
   ```csharp
   public sealed class DemoData : IRealObject
   {
       Task OnHostStartAsync( IActivityMonitor monitor, IServiceProvider services, IConfiguration configuration ) { ... }
   }
   ```
   The real objects (the `SqlTable`s, the `SqlPackage`s) are services: inject them as parameters, or get them from
   `services` (the `map.StObjs.Obtain<T>()` of a former host code becomes `services.GetRequiredService<T>()`):
   ```csharp
   Task OnHostStartAsync( IActivityMonitor monitor, UserTable users, UserPasswordTable passwords ) { ... }
   ```
   An exception fails the start of the host: a seeding that must not stop the host catches it (and logs a warning).

   **A real object that configures the endpoints** (its private `ConfigureServices` is called when the generated code
   is loaded):
   ```csharp
   public sealed class MyWebConfiguration : IRealObject
   {
       void ConfigureServices( StObjContextRoot.ServiceRegister services )
       {
           services.Services.AddHttpClient();
           // Applied to the WebApplicationBuilder of every endpoint (CK.AspNet).
           WebApplicationContributions.FindOrAdd( services.Services )
                                      .Add( web => web.AppendApplicationBuilder( app => app.UseForwardedHeaders() ) );
       }
   }
   ```
4. **The tests** build the host without starting it: the test project references the host project, and passes the
   content root and the host's assembly (the entry assembly of a test is the test runner):
   ```csharp
   var host = CKomposableAppHost.Build( [],
                                        b => b.Configuration.AddInMemoryCollection( overrides ),
                                        TestHelper.SolutionFolder.Combine( "XXX/XXX.Host" ),
                                        Assembly.Load( "XXX.Host" ) );
   await host.StartAsync();
   ```
   `configure` is called right after the creation of the builder, before the monitoring and the application identity
   are configured. `Assembly.Load( "XXX.Host" )`: the top-level `Program` classes of several hosts have the same name.

**Check:** `dotnet build` of the host project succeeds (it fails with an explicit `CK.AppHost:` error when the host is
not an executable or doesn't reference its builder); `#Dev/Parties/XXX.Host.json` exists after the build; the host
starts (`#Dev/Start.ps1`) and serves its endpoints and its client applications. CK-Sample-AspNetAuth (Auth3, Front,
Admin), the demo of CK-Ng-Zorro-Contrib and the samples of CK-Ng-User-UserProfile, CK-Ng-Admin and
CK-Observable-Domain (from `WebApplication` hosts: M14, M15 and M18) are migrated this way.

## M19. The account flows: the registration and the password recovery

Two security fixes of the anonymous account flows.

**The registration of an invited user registers the invitation's address** (CK.IO.UserManagement.UserInvitation,
CK.UserManagement.UserInvitation): `ICompleteRegistrationCommand.Email` is removed. The user's primary e-mail is the
address the invitation was sent to, registered as validated (the token proves its reception). Before, the command's
address was registered as validated: whoever held an invitation link registered any address.

**Detect:** `ICompleteRegistrationCommand` built in C# (`c.Email = ...`) or in TypeScript (`new
CompleteRegistrationCommand( email, firstName, ... )`); a call to `UserManagementService.CompleteRegistrationAsync`.

**Do:** remove the e-mail: `new CompleteRegistrationCommand( firstName, lastName, extendedCultureId, password, token )`,
`CompleteRegistrationAsync( ctx, firstName, lastName, token, password, extendedCultureId, userName )`. A registration
form shows the invited address (`IValidateInvitationTokenCommand` returns it) without sending it.

**The password recovery link is single use** (CK.UserProfile.UserPassword.Lost, behavior): the token is bound to the
user's current password, so the recovery kills it, and so does any other password change. Before, a link stayed
usable until it expired, after a successful recovery too. A link sent before the upgrade is refused (ask a new one:
the lifetime is short). `PasswordLostTokenService.CreateToken` takes the password hash
(`PasswordLostQueries.FindPasswordUserByEmailAsync` returns it), and `TryReadToken` is replaced by `ReadTokenAsync`
(a code that issues or reads the tokens itself follows).

**The primary e-mail of an actor is validated as soon as it has a validated e-mail** (CK.DB.Actor.ActorEMail,
behavior): `ActorEMailTable.AddEMail[Async]` with `isPrimary: true` on an address that is not validated (and not
validated by the call) while the actor has another validated address throws `EMail.PrimaryMustBeValidated`; un-validating
the primary address (`validate: false`) elects the most recently validated one. The recovery mail of a lost password
goes only to a validated primary address (as documented: the rule above makes it the actor's validated address).

**Detect:** `AddEMail( ..., isPrimary: true )` without `validate: true`, followed by `ValidateEMail`.

**Do:** validate in the same call: `AddEMail( ctx, actorId, userId, email, isPrimary: true, validate: true )` (an address
set by an administrator, or proved by a token), or add it as non primary and make it the primary one once validated.

## M20. The public URL of a party

A party states what it is to the others: its **public URL** and its **client applications** (`IParty.Description`,
CK.AppIdentity). The AuthCenter uses them, never a configured copy nor the request:
- **the links of the mails** (an invitation, a lost password) target the client application of the party through which
  the user acts (the caller party of the command);
- **the passkey origins** and **the OIDC callbacks** it accepts are the ones of the party that relays the ceremony or the
  login (its own party for its own endpoints, the remote that relays it otherwise).

**Where the description comes from (behavior):**
- **The public URL** is the `DefaultUrl` of the first endpoint of the party (the "HttpEndpoint" feature, M15), or its
  `Local:PublicUrl` when configured: an absolute `http` or `https` URL without path (a start-up error otherwise).
- **The client applications** are the ones it serves (CK.TS.AspNet.Clients, M14): the default one is served at `/`.
- **A remote's description** is announced over the channel when it connects (and again when it changes), and kept in
  its folder of the store (`PartyDescription.json`): it is known while the remote is not connected.

**Detect:** a party behind a reverse proxy or a public domain name (its endpoint's URL is not the one the browsers use);
a host that is not a party with the "HttpEndpoint" feature (a `WebApplication` host) and builds mails or serves passkeys
or OIDC callbacks; templates of the mails overridden by the application (`{{ frontUrl }}`); an own `IUserManagementMailer`
or `IPasswordLostMailer`; code that builds or reads the password recovery tokens (`PasswordLostTokenService`).

**Do:**
- **Behind a proxy:** configure the public URL of the party: `"Local": { "PublicUrl": "https://app.example.com" }`.
  A `WebApplication` host (no "HttpEndpoint" feature) configures it too.
- **The templates:** `{{ frontUrl }}` is `{{ clientUrl }}` (the default client application of the party);
  `{{ clientUrls.Name }}` is the one of another client application.
- **An own mailer:** `IUserManagementMailer.SendUserInvitationAsync` takes the full name of the issuing party
  (`string? issuingPartyFullName`) and returns whether the mail was sent; `IPasswordLostMailer.SendPasswordLostAsync`
  and `SendPasswordSetConfirmationAsync` take the full name of the caller party (`string? callerPartyFullName`) and
  return whether the mail was sent. The URL of the party is
  `CurrentLocalParty.LocalParty.FindCallerParty( fullName )?.Description.GetClientApplicationUrl()`.
- **The recovery tokens:** `PasswordLostTokenService.CreateToken( userId, passwordHash, issuingPartyFullName )` and
  `ReadTokenAsync( monitor, token, callerPartyFullName, getPasswordHashAsync )`.
- **The caller party** of a command is `AuthenticationInfo.CallerPartyFullName` (the full name of the party, null when
  it is unknown or not applicable): pass it to these methods.

**Behavior:**
- **No URL, no mail:** when the party through which the user acts has no public URL or no default client application,
  no mail is sent and an error is logged (the administrator who creates an invitation gets an error message; the
  anonymous password recovery answers as usual).
- **The tokens are bound to their party:** an invitation records the party through which it was issued
  (`IUserInvitation.IssuingPartyId`, CK.DB.UserInvitation 1.0.1; 0 for the invitations created before: redeemed
  through any party), a recovery token carries it: they are redeemed only through this party.
- **A URL relayed by a party** (an OIDC callback, the origin of a passkey ceremony) is accepted only on the origin of
  the public URL of **that** party (the caller party): a party can't start a login or a ceremony on the origin of
  another one, and an OIDC login is completed through the party that started it.

**Check:** the party's public URL is the one the browsers use (behind a proxy: `Local:PublicUrl`); a mail opens the
client application of the party where the request was made; a passkey ceremony and an OIDC login work from every front.
CK-Sample-AspNetAuth (its Auth3 configures none of these URLs) is migrated this way.

## M21. Angular 22 and the signal forms

The Angular packages (`CK.TS.Angular`, `CK.TS.Angular.Engine`, `CK.Ng.Zorro` and the `CK.Ng.*` packages) target
**Angular 22** and **ng-zorro-antd 22** (the released version targets Angular 20). The engine upgrades an Angular
application by itself; what no migration does is listed below.

**Before the first build:**
- **Node:** the Angular 22 CLI requires Node `^22.22.3`, `^24.15.0` or `>=26.0.0` (24.21.0 recommended); nvm-windows
  needs 1.2.2 or later (1.1.x cannot install Node 24 on x64). The setup and its checks are in
  [node-upgrade-angular-22.md](https://github.com/signature-opensource/CK-TypeScript/blob/stable/node-upgrade-angular-22.md)
  (CK-TypeScript). The requirement is the version: nvm-windows is the recommended way to install it, not a condition.
  An older Node: the upgrade refuses and names the required versions. Build servers need it too.
- **Commit (or stash) the Angular application folder:** an application with uncommitted changes is not upgraded and
  the build fails. Only `ck-gen`, `.yarn/` and `.yarnrc.yml` are ignored: an uncommitted `yarn.lock` blocks it (the rest
  of the repository doesn't).
- **A repository that owns Angular packages** (its `Res/` code or its transformers use `GenericFormData`,
  `FormControlConfig`, `passwordComplexityValidator`...) **migrates that code to the signal forms first** (below): the
  code generation fails on the removed types before the compile check, the upgrade is not verified and the next run
  undoes it.

**Do, the upgrade (automatic):** build the application's builder (its `*.Builder` project): CK.AppBuilder runs the
builder after its build, so the first `dotnet build` of the solution on the new packages starts the upgrade. The engine
upgrades yarn (4.8.1 becomes 4.18.1), runs `ng update` from 20 to 21, then 21 to 22, then a compile check (about 2
minutes per application), and logs a summary in the builder's `Logs/Text`: the files changed, the optional migrations not
run, a link to the Angular update guide (the changes no compiler sees). Review the diff and **commit it, before any
`ckli build`**: ckli resets a repository after building it, an upgrade done during a ckli build is thrown away (and runs
again at the next build). Commit with it the root `.yarnrc.yml`, the new `.yarn/releases/yarn-4.18.1.cjs` (4.8.1
deleted), and the application's new `.yarnrc.yml` and rewritten `yarn.lock`.
- A failed step is undone: the application is put back as it was, the half-done state is saved in a git stash that the
  message names. An upgrade that stops after its steps but before its compile check (a failed code generation) leaves
  the `.ck-angular-upgrade` marker in the application folder: the next run undoes it the same way. Before a rerun, drop
  the stash once read, and commit (or restore) the `yarn.lock` that yarn's upgrade rewrote.
- Compile errors after a good upgrade fail the build, with hints: fix them before committing. A rerun doesn't check
  again: check the fixes with `yarn ngc -p tsconfig.app.json --noEmit` in the application folder.
- Expect a large diff: Angular 21 converts every template to `@if` / `@for`; the Angular 22 migrations add
  `changeDetection: ChangeDetectionStrategy.Eager` to the components, the `extendedDiagnostics` of `tsconfig.app.json`
  and `provideNzDateFnsAdapter()` to `app.config.ts`; `@angular/platform-browser-dynamic` is replaced by
  `@angular/platform-browser`.
- **The upgrade keeps `@angular/animations`** (bumped to 22): remove it after the upgrade, with `provideAnimations()`
  (below): `yarn remove @angular/animations` in the application folder.
- The test applications of the `TSInlineTests` folders are upgraded by their test run: run the tests once outside ckli
  and commit the upgraded applications, as for a builder (their `package.json`, `yarn.lock`, `.yarnrc.yml`,
  `angular.json`, `jest.config.js`, `.yarn/sdks`).

## M27. The Yarn settings written by the TypeScript engine

The TypeScript engine (CK-TypeScript) writes two new things in the files of a repository, the first time it runs on
the new packages. In a CKli World, a build that changes a tracked file fails and lists it (a build impact): **build
these repositories with `ckli build --build-impacts commit` the first time**, then review what the build committed.

**Detect:**
- A `.gitignore` with a `.yarn/*` line (the Yarn section that the engine writes) and no `ck-install-state` line: every
  repository whose tests or builders run the TypeScript engine.
- An application (a client application, a test application in `TSInlineTests/`) that uses `CK.Ng.Zorro`: its
  `.yarnrc.yml` has no `packageExtensions` block for `ng-zorro-antd`.

**Do:**
- Nothing by hand: the engine writes both. Commit them (in a CKli World, `--build-impacts commit` does it). The
  `.gitignore` gets:

  ```
  # The install marker of the CK.TypeScript engine (it describes the local install).
  **/.yarn/ck-install-state
  ```

  and the `.yarnrc.yml` of an application with `CK.Ng.Zorro` gets:

  ```yaml
  packageExtensions:
    "ng-zorro-antd@*":
      peerDependencies:
        # CK.Ng.Zorro.ZorroPackage: ng-zorro-antd uses rxjs (through @angular/cdk and @ant-design/icons-angular) but doesn't declare it: without the peer, its CDK is a second instance.
        "rxjs": "*"
  ```

  Never revert them: the next run writes them again.
- **Optional, for a package of yours:** a `[TypeScriptPackage]` can declare the same settings for the third-party
  packages it brings (`CK.TypeScript` namespace):

  ```csharp
  // An entry of the packageExtensions of the application's .yarnrc.yml: an edge that a package doesn't declare.
  [YarnPackageExtension( "ng-zorro-antd@*", DependencyKind.PeerDependency, "rxjs", "*",
                         Reason = "ng-zorro-antd uses rxjs (through @angular/cdk and @ant-design/icons-angular) but doesn't declare it: without the peer, its CDK is a second instance." )]
  // An entry of the resolutions of the application's package.json: redirects a declared dependency.
  [PackageResolution( "is-number", "7.0.0", Reason = "Test resolution." )]
  ```

  The selector of a `[YarnPackageExtension]` needs a range (`"ng-zorro-antd@*"`); its kind is `Dependency` or
  `PeerDependency` (a `DevDependency` is an error).

**Behavior:**
- **One `@angular/cdk` instance:** without the peer, Yarn Plug'n'Play installed a second instance of the CDK under
  ng-zorro-antd: the CDK services seen by ng-zorro-antd and by the application were two different objects.

**Check:** a second build has no build impact; no "is installed as N instances" warning in the build logs.

## M30. The options of the party components: the engine of CK.AppIdentity, the forwarded headers

A package can add options to a feature driver or to a party client (`IPartyComponentOption<TOwner>`, `[FeatureOption]`,
`[PartyClientOption]`): the engine of CK.AppIdentity knows them, in their order, and generates the
`PartyComponentOptionDirectory` (a singleton of CK.AppIdentity). The "HttpEndpoint" feature uses it for the options of
its endpoints; the first one is `ForwardedHeaders`, for an endpoint behind a reverse proxy.

| Package | New or changed |
|---|---|
| CK.AppIdentity.Engine (new, CK-AppIdentity, `3.0.0-0.cris-auth.1.ci.37` and later) | The engine of CK.AppIdentity: generates the `PartyComponentOptionDirectory`. |
| CK.AppIdentity | `PartyComponentOptionDirectory`: implemented by CK.AppIdentity.Engine. |
| CK.AppIdentity.HttpEndpoint (CK-AspNet) | `HttpEndpointOption` (the base of the options of an endpoint), `ForwardedHeadersOption`. `HttpEndpointFeatureDriver` depends on the `PartyComponentOptionDirectory`. |
| CK.Testing.AspNetServer (CK-AspNet) | References CK.AppIdentity.Engine. |

**Detect:**
- a project that runs the engine (a Builder: it references `CK.AppBuilder`; a test: it references `CK.Testing.StObjEngine`)
  and whose BinPath contains CK.AppIdentity: the App of a party (it references CK.AppHost or CK.AppIdentity.HttpEndpoint),
  or any package that depends on CK.AppIdentity. Without the engine, the engine run fails: it can't load
  `CK.Setup.PartyComponentOptionDirectoryImpl, CK.AppIdentity.Engine`;
- a test that registers `typeof( HttpEndpointFeatureDriver )` in `FirstBinPath.Types` (explicit types, without the
  `HttpEndpointAssembly`);
- a key of a `CK-AppIdentity:Local:HttpEndpoint:{Name}` section other than `Urls`, `Kestrel` and `DefaultEndpoint`.

**Do:**
1. **A Builder** whose BinPath contains CK.AppIdentity references the engine, with its other engines:
   ```xml
   <PackageReference Include="CK.AppIdentity.Engine" Version="3.0.0-0.cris-auth.1.ci.37" />
   ```
   A Builder that references `CK.TypeScript.Engine` (directly or through the Angular engine) has nothing to add: the
   TypeScript engine brings it (CK.TypeScript references CK.AppIdentity.PartyClient, so every BinPath that uses
   TypeScript contains CK.AppIdentity).
2. **A test** that runs the engine with CK.AppIdentity in its BinPath references `CK.AppIdentity.Engine` too, unless it
   references `CK.Testing.AspNetServer` or `CK.TypeScript.Engine` (which bring it). A test that registers the types of the "HttpEndpoint" feature
   one by one adds `typeof( PartyComponentOptionDirectory )` to them (the `HttpEndpointAssembly` brings it).
3. **A party behind a reverse proxy** enables the forwarded headers on its endpoint, with the addresses of its proxies
   (the proxies are never trusted by default, not even the loopback):
   ```jsonc
   "HttpEndpoint": {
     "Main": {
       "Urls": "http://0.0.0.0:5300",
       "ForwardedHeaders": {
         "KnownProxies": "10.0.0.12",     // IP addresses, separated by ';' (or an array).
         "KnownNetworks": "10.0.0.0/8",   // CIDR networks, separated by ';' (or an array).
         "Headers": "XForwardedFor, XForwardedProto, XForwardedHost", // The default.
         "ForwardLimit": 1                // The default.
       }
     }
   }
   ```
   Without them, behind a proxy that terminates TLS, the endpoint sees `http://internal-host`: a remote login (OIDC)
   starts with the internal callback URL, that the AuthCenter refuses (it is not the public URL of the party); the
   session cookies are not `Secure` when the internal host is a loopback; a browser without fetch metadata
   (`Sec-Fetch-Site`) is refused by the same origin check (its `Origin` is the public one). `Local:PublicUrl` (M20) is
   still configured: it is the URL that the party gives (the links of the mails, the passkey origins).

**Behavior:** a key of an endpoint section that is neither `Urls`, `Kestrel`, `DefaultEndpoint` nor an option of the
endpoint (`ForwardedHeaders`) is an error that fails the initialization of the party. `"ForwardedHeaders": true`, a
`ForwardedHeaders` section without `KnownProxies` nor `KnownNetworks`, an invalid address or network and an unknown key
in it are errors too.

**Check:** the Builders and the tests that run the engine succeed; the log of a party behind a proxy shows the client's
address, and a remote login (OIDC) through the proxy completes. The references are CK-AspNet's
`ForwardedHeadersOptionTests` and CK-Cris-TypeScript's
`HttpAuthenticationTests.behind_a_reverse_proxy_the_session_route_needs_the_forwarded_headers_Async`.

## M31. The enlistment URL is derived: `EnlistRemoteUrl` is removed

The URL that a party hands to a party it doesn't know or doesn't trust (so that it can be enlisted,
`PeeringIssue.EnlistUrl` on the other side) was configured: the `EnlistRemoteUrl` key of a remote, of a `Local` or of
the `Defaults`, with its `{DomainName}` placeholder. It is now derived from the System: it is the URL of the **approval page**, a client
application whose TypeScript packages state `[PartyClientFact( "Enlistment", "app-identity/enlist" )]` (CK.Ng.AppIdentity.Enlistment
does), followed by the value of the fact (the path of the page). The parties announce the route to it
(`PartyDescription.Routes`, the "Enlistment" route), so that every party of the System knows it, even without a page of its
own. A route is accepted only toward an **authorized host**: the Authentication Center of the party states the hosts in
its signed System list, otherwise the `"RouteHosts"` configuration of the party does (CK.AppIdentity.TransportLayer).

**Detect:** `EnlistRemoteUrl` in an `appsettings.json`, a test identity or a configuration built in code.

**Do:** remove the key. A party that must hand an enlistment URL needs, somewhere in its System, a party that serves the
approval page (with a public URL: `Local:PublicUrl` behind a proxy, M20), authorized to host the "Enlistment" route:

```jsonc
// On the Authentication Center: its "Local:AuthCenter" section. The target is the one the page's party announces.
"RouteHosts": { "Enlistment": [ "Acme/$Admin/#Prod" ] }
```

Without Authentication Center, the same `"RouteHosts"` goes in the `"Local"` of each party, with the target:
`"RouteHosts": { "Enlistment": { "Acme/$Admin/#Prod": "https://admin.acme.com/app-identity/enlist" } }`.

**Behavior:**
- An `EnlistRemoteUrl` key fails the start of the party: "configures an "EnlistRemoteUrl": it is no more supported".
- Without approval page in the System (or without public URL on the party that serves it), no enlistment URL is handed
  (null), as when nothing was configured.
- A party whose routes have an authority refuses the "Enlistment" route of a host that is not authorized (a
  `SecurityCritical` warning names its announcer): no enlistment URL is handed. Without authority nor configuration, the
  routes are believed as announced (a warning says so).
- The facts of a client application are key/values: `[PartyClientFact( "Admin" )]` (a fact without value) keeps
  compiling.

**Check:** the party starts; `PartyDescription.Routes` of a party of the System has the "Enlistment" route once the
approval page is served. The references are CK-AppIdentity-Transport's `EnlistUrlTests` and `RouteTests`.
