# Migrating from v2026.282 to explo/cris-auth

This guide lists what a repository (or a World) that uses the CK stack must change to move from the
**v2026.282.0** release (`Published/v2026.282.0.json`) to the packages of the **`explo/cris-auth`** branch.

The branch replaces WebFrontAuth (`CK.AspNet.Auth` and the packages built on it) with an authentication made of Cris
commands and an **Authentication Center** (the "AuthCenter") reached over CK-AppIdentity. **An application uses one
stack:** an application that upgrades its CK packages to this version migrates its authentication at the same time.

Each item below has an identifier, a **Detect** step (what to search for: it is meant to be scripted), the **Do** step,
and sometimes a **Check**. Apply them in order: the package changes (M1) bring the compilation errors that the
following items fix.

## M1. The replaced packages

**Detect:** a `<PackageReference Include="..."/>` to one of the packages of the first column, in any `.csproj`; and the
same names as strings (`"CK.Cris.Auth"`...) in the engine configurations (`BinPathConfiguration.Assemblies`, builders,
tests).

**Do:** replace each reference by the package(s) of the second column, then update every other CK package to the
`explo/cris-auth` versions.

|---|---|
| `CK.Auth.Abstractions` | `CK.AuthenticationInfo` |
| `CK.AspNet.Auth` (WebFrontAuth) | `CK.Cris.AspNet.Authentication` + the AuthCenter packages (see M3) |
| `CK.DB.AspNet.Auth` | `CK.AppIdentity.Cris.AuthCenter.Local` (an application that is its own AuthCenter) |
| `CK.TS.AspNet.Auth` | `CK.Cris.AspNet.Authentication` (it carries the TypeScript `AuthService`) |
| `CK.Ng.AspNet.Auth` | `CK.Ng.Cris.AspNet.Authentication` |
| `CK.Ng.AspNet.Auth.Basic` | `CK.Ng.Cris.AspNet.Authentication.Basic` |
| `CK.Cris.Auth` | `CK.Cris.Authentication` |
| `CK.IO.Auth.Basic` | `CK.IO.Authentication.Basic` |
| `CK.Cris.AspNet.Auth.Basic` | `CK.Cris.Authentication.Basic` |
| `CK.Ng.Cris.AspNet.Auth` | `CK.Ng.Cris.AspNet.Authentication` |
| `CK.Testing.AspNetServer.Auth` | `CK.Testing.AppIdentity.Cris.AuthCenter` (see M8) |
| `CK.AspNet.ActorChannel`, `CK.Ng.AspNet.ActorChannel` | None: the push is removed (see M13) |
| `CK.DB.User.UserGoogle` (and `.AuthScope`, `.EMailColumns`, `.Profile`, `.RefreshToken`), `CK.DB.User.UserFacebook` (and `.AuthScope`), `CK.DB.User.UserGitHub` (and `.AuthScope`, `.RefreshToken`), `CK.DB.User.UserGitLab` (and `.AuthScope`), `CK.DB.User.UserTwitter` (and `.AccessToken`, `.AuthScope`, `.ScreenName`) | `CK.DB.User.UserOidc`: a remote login is an OpenID Connect scheme (`Oidc.<Suffix>`); the accounts are not migrated (see M9) |

| `CK.DB.Auth.AuthScope`, `CK.DB.Auth.AuthScope.Tests` | None: the OpenID Connect logins use no authorization scopes |

**These stay:** `CK.IO.Auth` (the command parts `ICommandAuthUnsafe`, `ICommandAuthNormal`, `ICommandAuthCritical`,
`ICommandAuthDeviceId`, `ICommandAuthImpersonation`, namespace `CK.Auth`: unchanged) and `CK.DB.Auth` (the users and
the providers).

OpenID Connect (`Oidc.<Suffix>`: `CK.DB.User.UserOidc`), plus the passwordless weak actors (`Weak`,
`CK.DB.Actor.WeakActor`, at most the Unsafe level).** The per-provider packages are dead (above): an application whose
users log in with Google, Facebook, GitHub, GitLab or Twitter configures the provider as an OpenID Connect scheme of its
AuthCenter, and its users' accounts must be bound to their OpenID Connect identity (see M9).

| `CK.Testing.AppIdentity.Cris.AuthCenter` | The test host of an application that is its own AuthCenter |

## M2. The CK-AppIdentity configuration: "Defaults", no inheritance

The `CK-AppIdentity` configuration no longer inherits a key from an enclosing level. Default values are written in
explicit **`"Defaults"`** sections, which can appear at every level (root, tenant domain, group).

**Detect:** in every `appsettings*.json`, in-memory configuration (`c["..."] = ...`) and `ApplicationIdentityServiceConfiguration.Create`
callback: a key at the root, a tenant domain or a group (a *structural* level) other than its identity and structure
keys.

The structural levels accept only: `FullName`, `DomainName`, `PartyName`, `EnvironmentName`, `Parties`, `Local`,
`Defaults`, and at the root `StoreRootPath`, `TrashBinRetention`, `StrictConfigurationMode`. **Any other key there is a
start-up error** whose message says to move it.

**Do:** for each such key:
- if it configures the application (the local party) itself, move it into the level's **`"Local"`** section;
- if it was meant as a default for the parties below (the remotes), move it into a **`"Defaults"`** section at that
  level;
- if it was both, write it in both.

```jsonc
// Before (the root key was inherited by the remotes)
"CK-AppIdentity": {
  "FullName": "Acme/$Server",
  "AllowFeatures": "SomeFeature",
  "ListeningAddress": [ "tcp:127.0.0.1:37300" ],
  "Parties": [ ... ]
}
// After
"CK-AppIdentity": {
  "FullName": "Acme/$Server",
  "Local": { "AllowFeatures": "SomeFeature" },
  "Defaults": { "ListeningAddress": [ "tcp:127.0.0.1:37300" ] },
  "Parties": [ ... ]
}
```

- `AllowFeatures` / `DisallowFeatures` stay a delta: the `"Defaults"` from the farthest to the nearest, then the
  party's own keys. The same for `Assemblies` / `DefaultAssembly`.
- A remote party's entry has no `"Local"` nor `"Defaults"`; a `"Defaults"` holds no identity or structure key.
- `"RootStorePath"` was a misspelling that was silently ignored: the key is **`StoreRootPath`**.

**Check:** the application starts without a configuration error, and a party that should allow a feature does (a
remote that relied on an inherited `AllowFeatures` now needs it in a `"Defaults"` or in its own entry).

## M3. The application host: WebFrontAuth becomes the AuthCenter

**Detect:** `AddWebFrontAuth(`, `WebFrontAuthOptions`, `new AuthenticationBuilder(`, `UseAuthentication()` used for
WebFrontAuth, `UseMiddleware<CrisMiddleware>()`, the `/.webfront` routes in clients.

**Choose the shape:**
- **One application** (the most common deployment: the front application directly on its backend party): the
  application **is its own AuthCenter**: `CK.AppIdentity.Cris.AuthCenter.Local` + `CK.Cris.AspNet.Authentication`.
- **Several applications:** one AuthCenter application (`.Local`, the database, the login providers) and fronts
  (`CK.AppIdentity.Cris.AuthCenter.Remote` + `CK.Cris.AspNet.Authentication`) connected to it by CK-AppIdentity. The
  reference is the CK-Sample-AspNetAuth repository (its `Backend`, `Front` and `Admin` hosts: a party is named after
  what it is, not after the feature it implements).

**Do (one application):**

1. The packages (in the application's "App" project): `CK.AppIdentity.Cris.AuthCenter.Local`,
   `CK.Cris.AspNet.Authentication`, and per login scheme its Angular package (`CK.Ng.Cris.AspNet.Authentication.Basic`...,
   see M7) or, without an Angular front, its `CK.Cris.Authentication.<Scheme>` package. The database providers stay (`CK.DB.User.UserPassword` for Basic: it holds the login
   provider of the scheme).
2. The host:
   ```csharp
   builder.AddApplicationIdentityServiceConfiguration();
   // No AddDataProtection(): CK.AppIdentity.KeyManagement registers it (see below).
   builder.Services.AddCrisAuthentication();
   // ... (no AddWebFrontAuth, no AuthenticationBuilder)
   var app = builder.CKBuild( map );
   app.UseRouting();
   // ... (no UseAuthentication for WebFrontAuth)
   app.UseCrisAuthentication();
   app.UseCris();
   ```
   `UseCrisAuthentication()` comes before `UseCris()`. `UseMiddleware<CrisMiddleware>()` is replaced by `UseCris()`.
   In one gesture on the builder: `builder.EnableCrisAuthentication()` (it enables Cris too). A host that is a party
   with the "HttpEndpoint" feature writes none of this (M15).

   `CK.AppIdentity.KeyManagement` registers the DataProtection, keyed on the identity's full name rather than the content
   root path: remove the host's `AddDataProtection()`. **This is a one-time break:** what was protected under the former
   discriminator can't be read anymore. That includes the identity keys (delete the party's folder in the identity store:
   the key is recreated, and the remotes that pinned it must pin it again) and the authentication cookies (the users log in
   again).
3. The configuration (`appsettings.json`): the local party allows the feature; its settings are its `"AuthCenter"`
   section.
   ```jsonc
   "CK-AppIdentity": {
     "FullName": "MyApp/$Server",
     "Local": {
       "AllowFeatures": "AuthCenter",
       "AuthCenter": {
         "SessionLifetime": "1.00:00:00",
         "CriticalLifetimes": { "Basic": "00:05:00" }
       }
     },
     "Parties": []
   }
   ```
   There is no `"AuthCenter": true` designation (it is an error): allowing the feature is the opt-in, and the name
   says what the party is: `"AuthCenter"` on the party that is the AuthCenter, `"AuthCenterRemote"` on its remotes.
   With several applications, the AuthCenter allows `"AuthCenter"` in its `"Local"` and `"AuthCenterRemote"` on its
   fronts; a front allows `"AuthCenterRemote"` in its `"Local"` and `"AuthCenter"` on the one remote that is its
   AuthCenter. A party that allows only the name of the other role fails the start.

**`CK.AspNet` is no longer brought by the authentication:** a host that used `UseCKMonitoring()`, `CKBuild( map )` or
`GetBuilderMonitor()` on a `WebApplicationBuilder` and got `CK.AspNet` only through `CK.AspNet.Auth` /
`CK.DB.AspNet.Auth` (or `CK.Ng.AspNet.ActorChannel`, see M13) fails to compile (CS1061 on these methods, or CS1501 when another `CKBuild` overload is found):
reference `CK.AspNet`.

**The WebFrontAuth options:**

| WebFrontAuthOptions | AuthCenter (`Local:AuthCenter`) |
|---|---|
| `ExpireTimeSpan`, `SlidingExpirationTime` | `SessionLifetime` (default 1 day; the session slides on each refresh) |
| `SchemesCriticalTimeSpan` | `CriticalLifetimes:<scheme>` (and `CriticalLifetime` for the other schemes) |
| (none) | `TokenLifetime` (default 10 minutes), `RefreshGraceWindow` (default 1 minute, at most 5) |

**The Critical level differs:** WebFrontAuth gave no Critical level unless `SchemesCriticalTimeSpan` said so; the
AuthCenter gives **5 minutes** of Critical level after a Basic or passkey login by default (`CriticalLifetime`).
`00:00:00` for a scheme means "never Critical". Password changes, passkey registration, impersonation and
administration require the Critical level.

**The HTTP routes:**
- `/.webfront/*` is gone. The session commands (login, refresh, logout, impersonation...) are Cris commands posted to
  **`/.cris/auth`**; the other commands go to `/.cris`.
- A bearer token is accepted **only with its session's binding cookie** (path `/.cris`): a stolen token alone is
  anonymous. The refresh secret is a cookie of path `/.cris/auth`.
- `/.cris` and `/.cris/auth` accept only a **same-origin** JSON `POST` (a cross-site `Origin` or `Sec-Fetch-Site` is
  refused with 403, another media type with 415). A front served from another origin must be served through the
  application (a proxy), not called with CORS.
- The authentication applies to the Cris commands only: there is no HTTP interceptor adding the token to other
  requests (controllers, files).

**`CK.DB.GuestActor`:** `GuestActorDirectLoginAllower` (a WebFrontAuth direct login of the guests) is removed; the
package keeps its data model. There is no guest login scheme in the new stack yet.

**Check:** a Basic login on `/.cris/auth` returns a `SessionResult` with a token; a Normal command sent with the token
(and the cookies) is accepted; after the logout, the same command is refused.

## M4. The C# authentication API

**Detect:** `IAuthenticationInfo`, `IUserInfo`, `StdAuthenticationTypeSystem`, `IAuthenticationTypeSystem`,
`AuthenticationInfoTokenService`, `IWebFrontAuth*`, `.User.UserId`, `.ActualUser`, `.UnsafeUser`, `IAuthenticationResult`,
`ILogoutCommand`, `IRefreshAuthenticationCommand`, `IPocoAuthenticationInfo`, `IPocoUserInfo`,
`CrisWebFrontAuthCommandHandler`, `using CK.AspNet.Auth`.

**Do:**

| Old (CK.Auth.Abstractions, CK.Cris.Auth, CK.IO.Auth.Basic) | New |
|---|---|
| `IAuthenticationInfo` (an ambient service) | `AuthenticationInfo` (sealed class, ambient service, namespace `CK.Core`, package `CK.AuthenticationInfo`) |
| `info.User`, `info.ActualUser` | `info.Actor`, `info.ActualActor` (the anonymous below the Normal level) |
| `info.UnsafeUser`, `info.UnsafeActualUser` | `info.UnsafeActor`, `info.UnsafeActualActor` |
| `user.UserId`, `user.UserName` | `actor.ActorId`, `actor.ActorName` |
| `info.Level`, `info.DeviceId` | `info.UnsafeActor.Level` (each actor has its level), `info.DeviceId` |
| `StdAuthenticationTypeSystem` ... `.Create( userInfo, expires )` | `AuthenticationInfo.Create( new ActorInfo( id, name, level ), expires, criticalExpires, deviceId, utcNow )` |
| The users read by WebFrontAuth | `IActorInfoProvider` (implemented by `CK.DB.Auth`) |
| `IBasicLoginCommand` (CK.IO.Auth.Basic) | `CK.IO.Authentication.Basic.IBasicLoginCommand` (result: `ISessionResult`) |
| `ILogoutCommand`, `IRefreshAuthenticationCommand` | `ILogoutSessionCommand`, `IRefreshSessionCommand` (CK.IO.Authentication) |
| `IAuthenticationResult` (`Info`, `Token`, `Success`) | `ISessionResult` (`Info`, `Token`, `Success`, `RememberMe`) |
| `CrisAuthenticationService` (CK.Cris.Auth) | `CrisAuthenticationService` (CK.Cris.Authentication, namespace `CK.Auth`): same validation of the parts |

- The validation messages of the parts keep their text ("Invalid authentication level: ...", "Invalid actor identifier:
  ...", "Invalid device identifier: ...") and get resource names (`Authentication.ActorMismatch`,
  `Authentication.NormalLevelRequired`, `Authentication.CriticalLevelRequired`).
- A command or event executed later (a delayed or background command) restores its `AuthenticationInfo` from its
  parts: the actors are read by the `IActorInfoProvider`, and the restoration fails if an actor is not found.
- A login provider of a scheme is an `ILoginProvider` (in the AuthCenter); a login is never handled in a database
  package: the scheme packages (`CK.Cris.Authentication.Basic`...) hold the session command handlers.
- Remove `using CK.Auth;` from a file that used only the old abstractions: without `CK.IO.Auth` in its references the
  namespace no longer exists (CS0234).

**Check:** the solution compiles without any reference to the old types.

## M5. The routed events are renamed local events

**Detect:** `[RoutedEvent]`, `[RoutedEventHandler]`, `RoutedEventAttribute`, `RoutedEventHandlerAttribute`,
`CrisPocoKind.RoutedEvent`, `CrisPocoKind.RoutedImmediateEvent`.

**Do:** `[RoutedEvent]` → `[LocalEvent]`, `[RoutedEventHandler]` → `[LocalEventHandler]`, `CrisPocoKind.RoutedEvent` →
`CrisPocoKind.LocalEvent`, `CrisPocoKind.RoutedImmediateEvent` → `CrisPocoKind.LocalImmediateEvent`. Same semantics:
these events are local notifications, raised where the command executes.

## M6. CK.Configuration: the lookup API is obsolete

The lookup methods that walk up the parent sections are `[Obsolete]` (they keep their semantics); a new API resolves a
key as "its own value, otherwise the nearest `"Defaults"` section above it".

**Detect:** the obsolete warnings (CS0618) on `TryLookupSection`, `TryLookupValue`, `LookupAllSection`,
`LookupAllSectionWithDistance`, the typed `TryLookupXxxValue` / `LookupXxxValue`, `AssemblyConfiguration.Create`.

**Do:** use `TryResolveSection`, `TryResolveValue`, `ResolveAllSection(WithDistance)`, `TryResolveXxxValue`,
`ResolveXxxValue`, `AssemblyConfiguration.Resolve`, and move the configuration values that relied on the parent lookup
into `"Defaults"` sections (`ConfigurationSectionExtension.DefaultsKey`). A configuration that is not a CK-AppIdentity
one can keep the obsolete API for now.

## M7. The TypeScript and Angular front

**Detect:** in the C# of the packages: `AspNetAuthPackage`, `AspNetAuthBasicPackage`, `CrisAspNetAuthPackage`,
`using CK.Ng.AspNet.Auth`, `using CK.Ng.Cris.AspNet.Auth`; in the TypeScript and the transformers (`*.t`):
`authenticationInfo().user`, `authenticationInfo().level`, `authenticationInfo().actualUser`,
`authenticationInfo.user`, `authenticationInfo.level`, `authService.basicLogin(`, `unsafeDirectLogin(`,
`availableSchemes`, `CK/Ng/AspNet/Auth/`.
- `authenticationInfo().unsafeActor` is the new API.
- A `basicLogin(` function that returns a `BasicLoginCommand` is the helper that M8 recommends.

Neither is a leftover.

**Do, the packages:**

| Old | New |
|---|---|
| `CK.Ng.AspNet.Auth.AspNetAuthPackage` | `CK.Ng.Cris.AspNet.Authentication.NgCrisAuthenticationPackage` |
| `CK.Ng.AspNet.Auth.Basic.AspNetAuthBasicPackage` | `CK.Ng.Cris.AspNet.Authentication.Basic.NgCrisAuthenticationBasicPackage` |
| `CK.Ng.Cris.AspNet.Auth.CrisAspNetAuthPackage` | `CK.Ng.Cris.AspNet.Authentication.NgCrisAuthenticationPackage` |
| `AuthenticationPageComponent`, `PrivatePageComponent`, `BasicLoginFormComponent`... (namespace `CK.Ng.AspNet.Auth[.Basic]`) | Same names, namespace `CK.Ng.Cris.AspNet.Authentication[.Basic]` |

- **The scheme handlers come with the front packages:** `CK.Ng.Cris.AspNet.Authentication.Basic` and `.Weak`, and
  `CK.Cris.AspNet.Authentication.Passkey` (brought by `CK.Ng.Cris.AspNet.Authentication.Passkey`), preserve their
  reference to `CK.Cris.Authentication.Basic`, `.Weak` and `.Passkey` (`[assembly: PreserveAssemblyReference]`): the
  engine finds the command handlers. A C#-only application (no Angular package) references and registers the
  `CK.Cris.Authentication.<Scheme>` packages itself.
- The routes are kept: `/auth` (the authentication page, with `?critical` to reach the Critical level), the private
  page at `/` (its `canMatch` tests `actor.actorId !== 0`).
- **The transformers:** the components keep their slots (`<PasswordLost />` of the Basic login form,
  `<PreUserInfoBoxNormalItems />`, `<PreAvatarFallbackComputing />`, `<PreDependencyInjection />`,
  `<PostLocalVariables />`...). A transformer that targets a generated file by its path changes it:
  `CK/Ng/AspNet/Auth/...` → `CK/Ng/Cris/AspNet/Authentication/...` (e.g.
  `CK/Ng/Cris/AspNet/Authentication/authentication-page/routes.ts`).

**Do, the API (`NgAuthService` signals, `AuthService`):**

| Old | New |
|---|---|
| `ngAuthService.authenticationInfo().level` | `ngAuthService.level()` |
| `ngAuthService.authenticationInfo().user.userId` | `ngAuthService.actor().actorId` |
| `ngAuthService.authenticationInfo().user.userName` | `ngAuthService.actor().actorName` |
| `ngAuthService.authenticationInfo().actualUser` | `ngAuthService.actualActor()`, `ngAuthService.isImpersonated()` |
| `authService.authenticationInfo.level` | `authService.level` (and `authService.actualLevel`) |

| `authService.basicLogin( userName, password )` | send a `BasicLoginCommand` through the `HttpCrisEndpoint` (`sendAsync` / `sendOrThrowAsync`): the `AuthService` follows every session command sent through the endpoint |

the browser.

## M8. The tests

**Detect:** `CK.Testing.AspNetServer.Auth`, `CreateRunningAspNetAuthenticationServerAsync`, `AddWebFrontAuth`,
`AddUnsafeAllowAllCors`, `AuthenticationBasicLoginAsync`, `AuthenticationLogoutAsync`, `basicLogin(` in the specs.

**Do, a C# test host that needs a real authentication** (`CK.Testing.AppIdentity.Cris.AuthCenter`, namespace
`CK.Testing`):

```csharp
var configuration = TestHelper.CreateDefaultEngineConfiguration();
configuration.FirstBinPath.Path = TestHelper.BinFolder;
// The application is its own AuthCenter (with its HTTP front).
configuration.FirstBinPath.AddAuthCenterApplication();
configuration.FirstBinPath.Assemblies.AddRange( ["CK.Ng.Cris.AspNet.Authentication.Basic", // Brings the Basic handler.
                                                 "CK.DB.User.UserPassword", // The actors and the Basic login provider.
                                                 ... ] );
// The HTTP front reads only the commands of the TypeScript type set: a test without TypeScript tooling uses
// TestHelper.GetTypeScriptGeneratedOnlyTargetProjectPath().
configuration.FirstBinPath.EnsureTypeScriptConfigurationAspect( targetProjectPath, ... );
var map = (await configuration.RunSuccessfullyAsync()).LoadMap();
await using var server = await WebApplication.CreateSlimBuilder().CreateRunningAuthCenterApplicationAsync( map );
```

- `CreateRunningAuthCenterApplicationAsync( map, identity, configureApplication )`: the identity defaults to
  `AuthCenterApplicationTestingExtensions.DefaultIdentity` ("Test/$AuthCenter", `"Local": { "AllowFeatures": "AuthCenter" }`);
  pass a callback to change it (e.g. `c["Local:AuthCenter:CriticalLifetimes:Basic"] = "00:00:00"` when a test needs a
  login below the Critical level).
- `AddUnsafeAllowAllCors()` is gone: remove it (the Cris endpoints require the same origin; the TypeScript runner
  targets the server's address).
- A `CreateAutomaticServices()` used to prepare the database now builds the AuthCenter's identity service: give it a
  configuration
  (`services.AddSingleton( ApplicationIdentityServiceConfiguration.Create( TestHelper.Monitor, AuthCenterApplicationTestingExtensions.DefaultIdentity )! );`: the DataProtection is registered by
  `CK.AppIdentity.KeyManagement`).
- A test that only needs a plain Cris server uses `CreateRunningAspNetServerAsync( map, app => app.UseCris() )`
  (CK.Testing.AspNetServer): it no longer needs an authentication.
- A C# client posts the session commands to `/.cris/auth` and keeps the cookies (the `RunningAspNetServer.Client` does);
  it sets `Client.Token` from the `ISessionResult`. A refused call's `ICrisResultError` read from the TypeScript type
  set cannot be read back by the Json import: check the response as text.
- A test that registered its own handler of `IUpdateUserCommand` (a `TestCommandHandler` copied from the samples)

- Delete the stale `$StObjGen/G0.cs` after the upgrade.

## M11. Poco `Clone()` and `Create<T>()`

Every Poco is now a factory of any other Poco (CK.StObj.Model, `PocoExtension`), with generated code (no reflection,
no serialization):

```csharp
T Clone<T>( this T poco ) where T : class, IPoco;                         // A deep copy.
T Create<T>( this IPoco source ) where T : class, IPoco;                  // A new T from what the source shares with it.
T Create<T>( this IPoco source, Action<T> configure ) where T : class, IPoco;
```

**`Create<T>` copies the shared parts only:** a property is copied when it is declared by an abstract Poco (a part,
`[CKTypeDefiner]`, like `ICommandCurrentCulture`, `ICommandAuthNormal`, `ICommandTargetParty`...) that both types
implement. Two properties that only have the same name are **not** copied. The copy is deep (nested Pocos and
collections are copied, immutable values are shared). Same type: a clone; nothing shared: a new default `T`.

**Detect (1), a result or a command built by copying from the command:** a command handler that takes a
`PocoDirectory` (or uses `cmd.CreateResult(...)`) and assigns properties of the command to the new Poco
(`r.X = cmd.X;`, `c.CurrentCultureName = cmd.CurrentCultureName;`, `c.ActorId = cmd.ActorId;`...).

**Do:** create the new Poco from the command: `cmd.Create<TResult>( r => ... )` (or `cmd.Create<INextCommand>( ... )`).
The `PocoDirectory` dependency of the handler often disappears, and so do the copies of the properties of the shared
parts. The properties that are not in a shared part are set explicitly: never create a part only to share them (a part
carries a semantics, like `ICommandCurrentCulture`; properties that merely have the same name are not one).

```csharp
// Before
[CommandHandler]
public async Task<IExecutionIdentity> HandleAsync( IAskLaterQCommand command, AuthenticationInfo info, PocoDirectory pocos, ... )
{
    var whoAmI = pocos.Create<IWhoAmIQCommand>( c =>
    {
        c.TargetPartyFullName = command.TargetPartyFullName;
        c.ActorId = info.Actor.ActorId;
    } );
    ...
// After: the ICommandAuthNormal part (the validated ActorId) is shared; TargetPartyFullName is not in a shared part.
[CommandHandler]
public async Task<IExecutionIdentity> HandleAsync( IAskLaterQCommand command, ... )
{
    var whoAmI = command.Create<IWhoAmIQCommand>( c => c.TargetPartyFullName = command.TargetPartyFullName );
    ...
```

`cmd.CreateResult(...)` (CK.Cris) is unchanged: it creates an empty result. Use it when the result shares nothing with
the command.

**Detect (2), a clone by serialization:** a Poco written to JSON and read back to copy it (`WriteJson` then `ReadJson`
of the same Poco, often in a helper named `Clone` or `DeepClone`).

**Do:** `poco.Clone()`. The semantics are the ones of the round-trip it replaces: a tree (a shared reference is copied
twice, a cycle is not supported).

## M14. The TypeScript configurations: package selection and client applications

A `<TypeScript>` configuration selects its packages, and it can be a **client application** that its host serves.

**The package selection (behavior):** the packages listed in the `<Types>` of a configuration are the roots of its
selection (when none is listed: all the non optional packages); the configuration gets their closure (computed from the
types: requirements, children, mappings), and its `<ExcludedTypes>` are never selected. Only the selected packages are
handled: their resources, their transformers, their `[RegisterTypeScriptType]` (the type set of the configuration) and
their npm libraries (`[TypeScriptImportLibrary]`). A type name of the `<Types>` or `<ExcludedTypes>` can be a pattern
(`"Acme.Front.*, Acme.Front"`, `"*, Acme.Commands"`): see the README of CK.TypeScript.

**The `/.cris` type set (behavior):** a request to `/.cris` is read with the type set of its `TypeFilterName` query
parameter ("TypeScript" when absent); an unknown `TypeFilterName` is a 400 Bad Request. The generated `HttpCrisEndpoint`
sends the one of its configuration; a raw request (a test, a `fetch`) to a named configuration passes it
(`/.cris?TypeFilterName=TypeScriptApp`).

**Detect:** in the builders and the `CKSetup.xml`: `TargetProjectPath`, `TypeFilterName`, `<Types>` that list packages,
`EnsureDefaultTypeScriptAspectConfiguration`; in the hosts: the serving of an Angular `dist` (`PhysicalFileProvider`,
`UseStaticFiles`, `MapFallbackToFile`), `MapForwarder` / `AddHttpForwarder` / `Yarp.ReverseProxy` to a dev server;
requests to `/.cris` outside the generated client.

**Do (recommended), the configuration:** name the configuration and give it its kind and its dev server port:

```xml
<TypeScript>
  <Multiple>
    <TypeScript Name="App" Kind="DefaultApp" DevServerPort="4200" />
    <TypeScript Name="MiniApp" Kind="App" DevServerPort="4201">
      <Types>...</Types>
    </TypeScript>
  </Multiple>
</TypeScript>
```

or, in a builder:

```csharp
var ts = builder.EnsureDefaultTypeScriptAspectConfiguration();
ts.Name = "App";
ts.Kind = ClientKind.DefaultApp;
ts.DevServerPort = 4300;
```

The other properties derive from the name: remove them.

**`EnsureDefaultTypeScriptAspectConfiguration()` (behavior):** it no longer sets the `TargetProjectPath` to
`{HostFolder}/{ApplicationName}.Web`: the engine derives it, `{ProjectPath}/Clients/{Name}` for a named configuration and
`{ProjectPath}/Client` for an unnamed one (the `ProjectPath` of a CKomposableAppBuilder's BinPath is the host folder). A
builder that calls it without a `Name` nor a `TargetProjectPath` and keeps its Angular project in the `{ApplicationName}.Web`
folder names the configuration (and moves the project to `Clients/{Name}`) or sets the `TargetProjectPath`.

| Property | Derived value |
|---|---|
| `TargetProjectPath` | `{ProjectPath}/Clients/{Name}` |
| `TypeFilterName` | `TypeScript{Name}`: an unnamed configuration keeps "TypeScript", so the requests of a renamed one change (see above) |
| Request path | `/` for the `DefaultApp` (at most one per BinPath), `/{kebab-name}` for an `App` (`MiniApp` → `/mini-app/`) |

The Angular engine writes the request path (`baseHref`) and the `DevServerPort` (`serve.options.port`) in the
`angular.json`. The host serves `dist/{folder}/browser` (the folder of the project: `App` for `Clients/App`): when an
existing Angular project moves to `Clients/{Name}`, rename its project in the `angular.json` to the folder name (and its
`buildTarget`s), remove its `outputPath` and, if the `name` of its `package.json` changes, run `yarn install` (otherwise
its dev server fails with "Package for ...@workspace:. not found in the project"). The `DevServerPort` is required for a client application and unique in its BinPath; the ports must also
differ between the hosts that run together.

**Do (recommended), the host:** reference `CK.TS.AspNet.Clients` from the application's assembly (the engine
generates the `ClientDirectory` of the host) and replace the hand-written serving of the Angular application (and its
`AddHttpForwarder()`, its `Yarp.ReverseProxy` reference) with `app.MapClients()`:

- In Development, the host starts the dev server of each client application (`ng serve --port {DevServerPort}` through
  the yarn of its project, stopped with the host; something already listening on the port is used instead) and
  forwards to it what it doesn't handle under the request path: the host stays the origin.
- Otherwise, it serves the built files (`dist/{project}/browser` of the client project) with a fallback to their
  `index.html`. A client application that is not built is skipped with a warning.
- `UseDist="true"` on the `<TypeScript>`, or the host configuration `Clients:UseDist` (all the client applications) or
  `Clients:{Name}:UseDist` (one of them), serves the built files in Development too: a test host that runs on the built
  application sets `Clients:UseDist` to `true`.

In one gesture on the builder: `builder.EnableClients()`. A host that is a party with the "HttpEndpoint" feature
calls nothing (M15).

**Check:** the host serves its client applications in Development (the dev servers start with it) and from their
`dist` otherwise. CK-Sample-AspNetAuth (the Front's App and MiniApp, the Admin's App) is migrated this way.

## M15. The host is a party: the "HttpEndpoint" feature

A host that serves HTTP is a **party** whose web server is a feature. It is a Generic Host whose "HttpEndpoint" feature
(`CK.AppIdentity.HttpEndpoint`, a static feature of the root party) starts one web application per endpoint of its
`Local:HttpEndpoint` configuration once the party is initialized, and stops them before the party stops. The packages
configure the web applications (their services and middlewares): the host's code doesn't depend on them. This is
optional: a `WebApplication` host keeps working (M3, M14).

**Detect:**
- a host built with `WebApplication.CreateBuilder` / `CreateSlimBuilder` that calls
  `AddApplicationIdentityServiceConfiguration()`;
- `AddCrisAuthentication()`, `UseCrisAuthentication()`, `UseCris()`, `MapClients()` in a host;
- a root `"Urls"` (or `"Kestrel"`) in its `appsettings.json`;
- `ASPNETCORE_ENVIRONMENT` or `applicationUrl` in its `launchSettings.json`.

**Do:**

1. **The package:** reference `CK.AppIdentity.HttpEndpoint` from the application's assembly (the "App" project).
2. **The host:** a Generic Host, with no pipeline code:
   ```csharp
   var builder = Host.CreateApplicationBuilder( new HostApplicationBuilderSettings { Args = args } );
   builder.UseCKMonitoring();
   builder.AddApplicationIdentityServiceConfiguration();
   // The monitor of the work outside the requests (the requests have the one of their ScopedHttpContext).
   builder.Services.AddScoped<IActivityMonitor, ActivityMonitor>();
   builder.Services.AddScoped( sp => sp.GetRequiredService<IActivityMonitor>().ParallelLogger );
   var monitor = builder.GetBuilderMonitor();
   var map = StObjContextRoot.Load( typeof( MyHost ).Assembly, monitor )
             ?? throw new InvalidOperationException( "Unable to load the generated code." );
   builder.Services.AddStObjMap( monitor, map );
   var host = builder.CKBuild();
   await host.RunAsync();
   ```
   - **Remove** `AddCrisAuthentication`, `UseCrisAuthentication`, `UseCris` and `MapClients`.
   - **The packages do it instead:** their real objects contribute `EnableCrisAuthentication`, `EnableCris` and
     `EnableClients` (`WebApplicationContributions`, CK.AspNet), and the feature applies them to every endpoint.
   - **An application adds its own configuration to an endpoint** with `builder.AddHttpEndpoint( "Main", web => ... )`,
     in one gesture on the `WebApplicationBuilder` (`web.AppendApplicationBuilder( app => ... )` for a middleware).
3. **The configuration:** the endpoints are configured with the party, not by the ASP.NET defaults.
   ```jsonc
   "CK-AppIdentity": {
     "FullName": "MyApp/$Front",
     "Local": {
       "AllowFeatures": "AuthCenterRemote, HttpEndpoint",
       "HttpEndpoint": { "Main": { "Urls": "http://localhost:5300" } }
     },
     ...
   }
   ```
   Each child of `Local:HttpEndpoint` is an endpoint, with `Urls` (separated by `;`) or a `Kestrel` section (Kestrel's
   own schema). Remove the root `"Urls"` / `"Kestrel"`.
4. **The launch profile:** a Generic Host reads `DOTNET_ENVIRONMENT`, not `ASPNETCORE_ENVIRONMENT`. Remove the
   `applicationUrl`: it sets `ASPNETCORE_URLS`.
5. **The tests:** the host is an `IHost` (`StopAsync` then `Dispose`). A test address is set with
   `CK-AppIdentity:Local:HttpEndpoint:Main:Urls`; a port 0 is resolved, and `HttpEndpointFeatureDriver.Endpoints`
   gives the actual address.

**Behavior:**
- **In Development, the ASP.NET defaults are an error:** the root `urls`, `http_ports` and `https_ports` keys and
  `Kestrel` section, and the `ASPNETCORE_URLS`, `ASPNETCORE_HTTP_PORTS` and `ASPNETCORE_HTTPS_PORTS` environment
  variables. Otherwise they are a warning, and they are ignored.
- **The web applications start once the party is initialized** (all its features set up) and stop before it: no
  request reaches a party that is not whole. A web application that stops by itself stops the host.
- **Only the root party has endpoints,** and every endpoint gets every contribution of the BinPath. A tenant domain
  that allows the feature is an error.
- **The web applications get the host's services:** the singletons are the host's (one instance); the
  container-configured services (`CrisAspNetService`...) are created per web application.

**A `WebApplication` host that stays one** can use the same one-gesture extensions instead of the pairs of M3 and M14:
`builder.EnableCrisAuthentication()` (which enables Cris) and `builder.EnableClients()`, before `CKBuild( map )`.
`CKBuild` doesn't apply the contributions of the packages: such a host calls them itself.

**Check:** the host starts and serves `/.cris` and its client applications (in Development, through their dev
servers). CK-Sample-AspNetAuth (the Front and the Admin) is migrated this way.

## M16. The `#Dev` folder of a development solution

The development data of a solution is in a `#Dev` folder at the root of its git working folder (each worktree has its
own). It is automatic: nothing to commit, nothing to configure (CK.AppIdentity.Hosting).
- **The build of each party creates it** (a party: an executable that is not a test project and has an
  `appsettings.json`, or `<CKAppIdentityParty>true</CKAppIdentityParty>`): its `.gitignore` is `*` (git ignores its
  content), the manifest of the party (`#Dev/Parties`), and the launcher `#Dev/Start.ps1`.
  `<CKAppIdentityDevFolder>false</CKAppIdentityDevFolder>` opts a project out.
- **A host in Development uses `#Dev/Store`** when it doesn't configure its `StoreRootPath`: its identity keys, its
  pinned remotes, its running status. Before, it used the store of the user's profile (shared by every checkout).
- **`#Dev/Start.ps1`** builds the parties, starts them in Development, waits until they are ready (their outgoing
  remotes connected, their HTTP endpoints started, their client applications served), prints their URLs and opens the
  browser; Enter stops them (`-SkipBuild`, `-NoBrowser`, `-Timeout`). It replaces the hand-written launch scripts.

To migrate:
1. Remove a committed `#Dev/.gitignore` (the build writes its own) and a `StoreRootPath` that points to the `#Dev/Store`
   of the solution (like `"../../#Dev/Store"`): the hosts in Development use it anyway. Moving the existing identity
   keys is not required (the parties pin each other again, `AutoTrustKey`).
2. Replace a hand-written launch script of the solution by `#Dev/Start.ps1`.
3. The tests that set `ApplicationIdentityServiceConfiguration.DefaultStoreRootPath` keep their own store (setting it
   disables the dev store); a test of the running status uses the `Create` overload with an explicit `devStoreRootPath`.

**Check:** after a build, `#Dev/Start.ps1` starts the parties and `git status` shows nothing of `#Dev`.
CK-Sample-AspNetAuth is migrated this way.
